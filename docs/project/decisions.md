# Decisions

Append-only decision log. Each row: what was decided, why, how reversible it is, and
who decided. See [`fsamuels/sdlc-standards`](https://github.com/fsamuels/sdlc-standards)
for the format this table follows.

| D-1 | 2026-09-14 | Adopt `fsamuels/sdlc-standards` full layer (standards + skills) | Keep branch naming, docs organization, and PR process consistent with other projects on the same account from day one, rather than drifting and reconciling later | Easy — two `.claude/settings.json` keys plus a few vendored files | fsamuels |
| D-2 | 2026-09-14 | Choose Godot 4 as the engine | Fast iteration and low motivation-risk outweigh Unreal's higher photorealism ceiling, which this project isn't targeting anyway (see README non-goals); Godot's plain-text project files are also the only one of the three a Claude Code cloud session can meaningfully edit | Moderate — asset/logic work invested in Godot won't carry over automatically, though 3D assets (glTF/FBX, PBR textures) port to another engine if needed later | fsamuels |
| D-3 | 2026-09-14 | Start Phase 2 layout blockout before drone capture, using a provisional square boundary sized to the confirmed 24.06-acre parcel total and a placeholder building box, rather than waiting on real GIS/orthomosaic data | Makes visible progress possible while capture is pending; county GIS/parcel viewers are interactive-only and not fetchable headlessly, so exact boundary shape and building footprints aren't available yet | Easy — boundary mesh and building position are explicitly placeholder and get replaced wholesale once real data lands | fsamuels |
| D-4 | 2026-09-14 | Pull the real parcel boundary from the WA State Geospatial Open Data Portal's public `Current_Parcels` ArcGIS `FeatureServer`, queried directly by parcel ID, instead of exporting from the county's own GIS viewer | The county GIS viewer and property search site are JS-driven Esri apps with no visible download option; the state portal republishes the same county assessor parcel data through a public REST endpoint that returns GeoJSON directly, headlessly, superseding the "interactive-only" constraint noted in D-3 | Easy — a GeoJSON file with a documented query, no dependency introduced | fsamuels |
| D-5 | 2026-09-14 | Approximate building footprints from Overture Maps' ML-derived buildings dataset (public S3, queried via DuckDB) rather than tracing them by hand from satellite imagery, since no surveyed county building-footprint layer covers this parcel | Manual tracing from Google Maps/satellite imagery is slow and error-prone; Overture's dataset gives real polygon shapes and rough heights headlessly, at the cost of being an ML approximation rather than surveyed data | Easy — clearly labeled as approximate in `docs/parcel-data.md`; wholesale replacement once real/orthomosaic data lands, same as the D-3 placeholder building box | fsamuels |
| D-6 | 2026-09-14 | Replace the D-3 provisional square boundary and single placeholder building with the real boundary/building data (D-4, D-5) directly in `main.tscn`, using an equirectangular lon/lat→meters projection centered on the parcel's area centroid as the scene's local origin, and unit-sized `BoxMesh`/`BoxShape3D` sub-resources scaled per-node (rather than a distinct sized sub-resource per fence segment/building) | Keeps the .tscn small (13 fence segments + 7 buildings share 2 unit meshes total) instead of ~20 near-duplicate sized sub-resources; equirectangular projection is simple and sufficiently accurate at this scale (a ~450m-wide parcel) versus a full geodesic/UTM projection | Moderate — coordinate origin and axis convention (`+X`=east, `+Z`=south) are now a scene-wide assumption; any future real-world-data import (orthomosaic, drone terrain) needs to reuse the same convention or everything needs re-deriving | fsamuels |
| D-7 | 2026-09-14 | Texture the ground plane with public NAIP aerial imagery (USGS National Map `USGSNAIPPlus` ImageServer, queried headlessly for the same bbox as the ground plane's real-world extent) instead of the flat placeholder color, and store the fetched PNG under `project/textures/ground/` rather than `assets/orthomosaic/` | Free, public-domain, ~0.6–1m resolution imagery gives the case map a real-looking ground texture (roads, tree lines, structures roughly in place) while drone capture is pending, same "pull what's headlessly available now, replace wholesale later" pattern as D-4/D-5; `assets/` isn't reachable from Godot's `res://` root, so the texture the scene loads has to live inside `project/` | Easy — one PNG plus a texture reference in `main.tscn`; swapped out wholesale once the drone-derived orthomosaic (D-3's eventual replacement) is ready, same as the boundary/building placeholders | fsamuels |
| D-8 | 2026-09-14 | Extract the player, fence segment, and building out of `main.tscn` into their own reusable scenes (`player.tscn`, `fence_segment.tscn`, `building.tscn`), instanced into `main.tscn` with only a per-instance `transform` override, instead of each of the 20 fence/building copies carrying its own full node subtree inline | `main.tscn` was on track to grow linearly (~10-12 lines per object) through every future addition (Phase 4-6: vegetation, animals, more buildings), making the file increasingly slow to work with and diff-noisy; instancing means future additions are one node block each, and each shared scene can later diverge per-instance (e.g. a distinct texture per building) via child-node property overrides without touching the blueprint scene | Easy — behavior-preserving; every fence/building transform value was carried over unchanged, verified headlessly before/after | fsamuels |
| D-9 | 2026-09-14 | Use a free CC0 rigged/animated horse model (Quaternius's Farm Animal Pack, via [poly.pizza](https://poly.pizza/m/F8HAAcLeBL)) for the first horse, ahead of the plan's own ordering (Phase 5 was meant to wait until the base environment was solid; the user asked for a real model with wander movement now) | Modeling/rigging/animating a horse from scratch is far more effort than this project's placeholder-first pattern justifies; Quaternius's pack is public domain (no attribution required, unlike CC-BY), already rigged with Idle/Walk/Run/etc. animations, and ships as glTF — no format conversion needed for Godot | Easy — a single `.glb` file plus one wrapper scene (`horse.tscn`) and one script (`horse.gd`); swappable for a different or higher-fidelity model later without touching the wander logic | fsamuels |
| D-10 | 2026-09-14 | Use three "Poly by Google" models (Hen, Rooster, Coyote, via poly.pizza) at the user's direct request, even though — unlike the D-9 horse — they're CC BY 3.0 (attribution required) and unrigged (no animations; movement is a plain translate+rotate, no walk cycle) | These were the specific models the user linked; recorded here so the CC-BY attribution requirement doesn't get lost — satisfied by [docs/credits.md](../credits.md). The lack of animation is a real, disclosed limitation, not a bug: obj2gltf-converted Poly assets ship as a single static mesh with no armature | Easy to swap for a rigged/CC0 alternative later if the lack of a walk cycle bothers the user; the attribution requirement itself is a one-way constraint for as long as these specific files are in the repo | fsamuels |
| D-11 | 2026-09-15 | Replace the boxy placeholder fence with a procedurally-generated wire/post fence (`fence_segment.gd`, a `@tool` script driven by an exported `length` in meters), and add a separate treeline ring 20m outside the real parcel boundary (`tree_line_segment.gd`, same pattern) as the actual hard edge of the explorable map, using a free CC0 tree model (Quaternius, via [poly.pizza](https://poly.pizza/m/qZtx0AHhcy)) | The old fence (one `BoxMesh` non-uniformly scaled per instance) looked like a solid wall, not a real pasture fence, and doubled as both the property line and the world's hard edge — which reads as "boxed in" right at the boundary. Splitting the two (thin fence at the true line, natural-looking treeline further out as the actual limit) matches common open-world practice; per-segment procedural generation avoids the non-uniform-scale-stretches-post-thickness problem a static mesh would have across 13 segments ranging 4.8m–435m long. The treeline's outward direction per segment is computed from which side of each edge's midpoint is farther from the boundary polygon's centroid — a per-edge approximation, not a true polygon offset, so corners aren't mitered (acceptable for an irregular tree line, not for a precise fence) | Moderate — the fence scenes changed shape entirely (from a static mesh to a script-generated one), so `fence_segment.tscn` and every `Fence_XX`/`TreeLine_XX` transform in `main.tscn` changed together; reversible by reverting this commit, but not a small diff | fsamuels |
| D-12 | 2026-09-15 | Regenerate every `Fence_XX`/`TreeLine_XX` transform in `main.tscn` directly from the source GeoJSON, using the polygon's true area-weighted centroid as the projection origin, rather than continuing to reuse the D-6 boundary data (only partially fixed by the earlier straighten-fence-segments bugfix, which fixed orthogonality but not absolute direction) | Making the fence a real, visible wire/post fence (D-11) exposed that the boundary never actually traced the real polygon shape — several segments' directions were wrong (e.g. one stored as due-east was actually due-south) despite correct lengths and roughly correct positions, so the earlier bugfix's "make each box non-skewed" fix was necessary but not sufficient. Caught by the user visually reviewing D-11 in the editor before merging, not by any automated check. Verified the fix by cross-checking the new projection reproduces the existing building positions almost exactly and that walking the 13 edges closes the polygon with ~0 error | Easy — same pattern as D-6/the earlier bugfix, wholesale replacement of the affected transforms with no dependent code changes; the deeper lesson (verify against an independent source, like building positions or polygon closure, not just internal self-consistency like axis orthogonality) doesn't have a "revert" but should inform any future re-derivation of this data | fsamuels |
| D-13 | 2026-09-15 | Build the minimap (`scenes/minimap.tscn`, `scripts/minimap.gd`) as a static 2D overlay reusing the existing NAIP ground texture as its background, with the player's world position mapped onto it via a linear formula, rather than a live top-down `Camera3D`→`SubViewport` render | The NAIP texture already covers exactly the ground plane's 520m×520m extent 1:1 (D-7), so the world-to-map mapping is a single linear transform, not a rendering pipeline; a live camera would auto-reflect future world changes and could rotate with the player, but costs an extra render pass the static approach doesn't need. The mapping (`(world - ground_origin + half_extent) / extent` for both axes, no flip) was verified empirically — not assumed — by inspecting the actual `PlaneMesh` vertex/UV pairs, then cross-checked against a live scene: the player's spawn position lands at the expected pixel and the derived facing rotation matches the direction the player was hand-oriented to face (west, into the property, away from the road) | Easy — a self-contained scene/script pair with two exported constants (`ground_origin`, `ground_half_extent`); swappable for a live-rendered version later without touching how it's wired into `main.tscn` | fsamuels |
| D-14 | 2026-09-15 | Recompute each treeline segment's outward direction (D-11) by actually testing whether a point 5m past the segment in that direction falls outside the real polygon (ray-casting point-in-polygon), instead of the original "farther from the polygon's centroid" distance heuristic | The user spotted a treeline segment sitting inside the fence instead of outside it. The centroid-distance heuristic is only reliable for a roughly convex, roughly centroid-symmetric shape; this parcel isn't one (D-12 already established it's irregular with one 435m edge), and it got 2 of 13 segments backwards — both now confirmed correct by the same point-in-polygon test that also validated D-12's fix. This is the second time a "seems reasonable" geometric shortcut for this boundary turned out wrong under an actual correctness check rather than a plausibility check | Easy — only the 2 wrong `TreeLine_XX` transforms changed, fence positions were never affected by this bug | fsamuels |
| D-15 | 2026-09-15 | Add 3 ducks (Mallard duck and Duck, both Poly by Google; a second Duck by madtrollstudio) at the user's direct links, all CC BY 3.0, near coordinates the user gave in relative terms ("50m to the left of the Back Barn" — interpreted as due west, `-X`, matching the minimap's east-is-right convention) | Same pattern as D-10: user-specified models, CC-BY so attribution-required (added to credits.md), unrigged/no animation (reuse `scripts/wander.gd`, no new script needed). Each duck's scale factor was derived independently from its own bounding box (target ~0.28m standing height) since, as with the earlier Poly-by-Google assets, there's no shared unit convention across different original artists' files — confirmed once again by wildly different raw bounding boxes (0.15, 0.4, and 54.2 as the three resulting scale factors) | Easy — 3 small wrapper scenes reusing an existing script, no new code; "left" was assumed to mean west and hasn't been visually confirmed | fsamuels |
